# Architecture decisions

Decisions already made, with the alternative that was rejected and why. Append new ADRs here as you make judgment calls the spec did not cover.

| ID | Decision | Rejected alternative | Reason |
|---|---|---|---|
| ADR-001 | Temporal (control) + Ray (compute) | Airflow / Argo / Kubeflow Pipelines | Static-DAG engines compile then walk; an agent operator makes the DAG dynamically unknown. Need durable execution, not DAG compilation. |
| ADR-002 | Temporal over Flyte 2 | Flyte 2 | More elegant single-system answer, but GA'd Aug 2026 with 2 core contributors and one commercial sponsor. This runs for years under real capital. Revisit in 18 months. |

| ADR-005 | DuckDB embedded per backtest worker | Shared analytical cluster for backtests | Isolation by construction; one tenant's scan cannot stall another's. |
| ADR-006 | ClickHouse for shared analytics, deferred until >~10 concurrent analysts | ClickHouse from day 1 | Operational cost without a query-concurrency problem to solve. |
| ADR-007 | Postgres + pgvector, exact kNN, no ANN index | Dedicated vector DB (Qdrant/Milvus/LanceDB) | See R-14. Revisit past ~1M vectors with measured p99 failure. |
| ADR-008 | Iceberg v3 as table format | Delta Lake | `timestamp_ns` (explicitly motivated by trading), deletion vectors, row lineage, variant type. |
| ADR-009 | Polars for the single feature runtime | Separate Spark backfill + streaming impl | Two implementations diverge permanently; unification is only achievable before the second exists. |
| ADR-010 | NATS JetStream → stateless SSE gateways | Websocket per run | Connections must scale with viewers, not runs. |
| ADR-011 | Reject kdb+ | kdb+ | The 161× benchmark is vendor-run on its home turf; honest reading is a narrow as-of/last-value win. Licence and hiring cost not justified. |
| ADR-012 | No scalar `score` column in the outcome type | Single composite score | Makes "this model is optimal" unrepresentable. Selection requires an explicit objective + constraint set. |
| ADR-013 | Approval envelopes, not per-action prompts | Per-action human approval | Users approve ~93% of prompts. Per-action approval buys the feeling of control and none of the substance. Gate four specific things. |
| ADR-014 | Skip skill libraries; use tiered memory with a 4K injection cap | Voyager-style skill library | SkillEvolBench: raw-trajectory reuse frequently beats distilled skills; static curated skills underperformed no-skill by −2.44 points. |
| ADR-015 | Small environment-grounded PRM (M13) for step criticism | LLM-as-judge | A 4B ternary-reward PRM beat 72B generic PRMs and 235B self-rewarding (+7–11% Best-of-N). Judges triage; gates decide. |
| ADR-016 | Single-agent by default; multi-agent only for genuinely parallel work | Orchestrator/worker everywhere | +90.2% reported, but at ~15× token cost with token usage explaining 80% of variance. Under equal budgets, single-agent matched or beat every MAS variant. |
| ADR-017 | One global LoRA adapter when M12 ships; personalize by retrieval | Per-tenant adapters | Multi-adapter serving savings assume adapters share a batch; tenant load here is correlated (market open, vol spikes) ⇒ cache thrash at peak. |
| ADR-018 | Hierarchical partial pooling for per-tenant adaptation | One-hot `tenant_id` in a global model | The one-hot is an invitation to memorize a tenant. |
| ADR-019 | WORM scope limited to ledger anchors + traded-model artifacts | WORM on analytical tables | SEC 17a-4's 2022 audit-trail alternative is satisfied by a hash-chained bitemporal ledger. WORM on analytics blocks compaction and re-partitioning forever. |
| ADR-020 | Fixed post-hoc pipeline (soup → ensemble → calibrate → closed-form threshold) | Threshold tuning as a search dimension | A tuned threshold is another trial and must be counted as one. Closed-form from the cost matrix avoids the count. |

## Phase 0 implementation ADRs (this codebase, 2026-09-13)

Judgment calls the spec did not cover, made while retrofitting an existing system rather than building a greenfield one.

| ID | Decision | Rejected alternative | Reason |
|---|---|---|---|
| ADR-P0-01 | The trial ledger is a **new** table (`backtest_trials`), separate from the existing content-addressed `backtest_runs` | Adding ledger columns to `backtest_runs` | `backtest_runs` is keyed by `run_id = sha256(RunConfig)` and is idempotent — re-running an identical config writes nothing. That is correct for an artifact cache and dishonest for a trial counter: the second look at a config is still a look and must count toward `N_eff` (§12.4, INV-22). Separating them lets dedup save compute without saving trial count. A deduplicated dispatch gets its own ledger row in state `deduplicated`, naming the artifact it reused. |
| ADR-P0-02 | INV-16 is enforced by a **type**: `RunExecutor::execute` takes a `&TrialTicket`, and `TrialTicket` has no public constructor — only `TrialLedger::register` mints one | A runtime check inside the executor, or a code-review rule | CLAUDE.md §2 requires "a schema constraint, a permission grant, a CI test, or a type — not documentation." A runtime check can be bypassed by a new executor implementation that forgets it; an unconstructable argument cannot. This also closes the test-fixture hole CLAUDE.md §3 names explicitly: there is no `#[cfg(test)]` constructor, so tests must register real trials too. |
| ADR-P0-03 | Keep **SHA-256** for content addressing and the hash chain, rather than migrating to blake3 | blake3 everywhere, per CLAUDE.md §4 conventions | The existing `run_id` content addresses are SHA-256 and are already persisted. Re-hashing would invalidate every stored `run_id`, break the dedup cache, and orphan existing `backtest_runs` rows — destroying information to gain speed, not correctness. The convention's real requirement is "same function everywhere," which SHA-256 already satisfies here. Postgres 11+ also exposes `sha256()` as a core function, so the chain trigger needs no extension. **Flagged for confirmation** — if blake3 is wanted, it should be a deliberate one-time migration, not a silent divergence. |
| ADR-P0-04 | A grid sweep logs `propensity = dispatched/expanded` (i.e. `1.0` when the whole grid runs) under `policy_id = 'grid_exhaustive'` | Refusing to register exhaustive sweeps, or logging a fake sub-1 propensity | INV-20 forbids *deterministic selection* policies because they make off-policy evaluation impossible. Exhaustive enumeration is not a selection policy — there is no counterfactual, and `p(dispatched | grid) = 1` is the **true** probability, not a placeholder. Off-policy estimators over an exhaustive sweep are trivially unbiased. When the budget truncates the expansion, the surviving fraction is the honest propensity, and that is what is logged. |
| ADR-P0-05 | The hash chain is computed by a **Postgres trigger**, and verified by an independent Rust reimplementation (`TrialRow::recompute_hash`) | Computing the chain in application code only | INV-19 names "DB trigger computes `row_hash`" as the mechanism: an application that forgets cannot then write an unchained row. Keeping a second, independent implementation in Rust is deliberate duplication — a chain that only ever agrees with itself proves nothing, so `verify_chain` recomputes from a different codebase. Numeric fields are hashed via `float8send()` (exact IEEE-754 bytes) because a float's text rendering is not a stable hash input. |
| ADR-P0-06 | `backtest_trials` registration facts are immutable by trigger; lifecycle columns (`state`, `started_at`, `ended_at`, `censoring`, `run_id`) may advance forward only | Strict append-only with no UPDATE grant at all (literal INV-19) | INV-19 says "no UPDATE grant on the trial table," but SPEC §4.1 puts `state`, `started_at` and `ended_at` on that same row and §9 defines a state machine over them — the two cannot both be satisfied literally. The resolution preserves the invariant's *purpose*: everything the hash chain covers (config, propensity, prereg, actor, exploration flag) is refused on UPDATE, terminal states cannot be re-entered or changed, and DELETE is impossible. **This is a partial enforcement of INV-19 and is reported as such** — see PROGRESS.md. |
| ADR-P0-07 | Iceberg items 0.1–0.3 are **N/A** for this codebase | Implementing them, or marking them done | There is no Iceberg (or Delta) anywhere in the workspace — storage is ClickHouse + Postgres + object storage. The retention landmine the spec warns about (5-day snapshot expiry) does not exist here because the mechanism it applies to does not exist. Recorded rather than silently skipped, so the checklist item is not mistaken for oversight. If Iceberg is ever introduced, S-1 must be set **before** the first write. |
| ADR-P0-08 | `delta_practical` is declared on the **Experiment** (at creation) and hash-locked into every trial's `prereg_hash`, with no serde default | Accepting it per-dispatch, or defaulting it | SPEC §4.1 says REQUIRED with no default; §2.1 says DEFINE refuses to start without it. Putting it on the campaign means the practically-meaningful effect size is fixed before any result exists. Omitting `#[serde(default)]` makes a request that leaves it out fail to deserialize — the boundary enforces it, not a validator that could be skipped. |
| ADR-P0-09 | Legacy rows record `delta_practical = NULL` ("never declared"), paired with `policy_id='legacy_unlogged'` by CHECK | `delta_practical = 0.0` for legacy rows | `0.0` is a *claim* — "any improvement counts" — that nobody actually made, and it would make legacy trials look trivially passable to anyone reading the column without also reading the policy marker. NULL is the truth. Pairing it to the legacy marker with the same CHECK shape used for propensity means there are exactly two ways to register (declare your effect size, or be explicitly marked legacy) and no third. |
| ADR-P0-10 | The legacy `POST /api/backtests` path registers a trial rather than being retired immediately | Retiring the route now; or leaving it unlogged until the frontend moves | Retiring it needs frontend work the correctness fix should not wait on, and leaving it unlogged means every one-off UI backtest is a look `N_eff` never sees — which makes deflation **too lenient**, the direction that flatters results. Registering it under the legacy marker closes INV-16 across every dispatch path now. Retiring the route (OQ-08 option A) remains the better end state. |
| ADR-P0-11 | §7 multi-tenancy (RLS, feature firewall, tenant grants) deferred entirely | Building tenant isolation ahead of a second tenant | Phase 0 is reserved for work where delay destroys unrecoverable information; there is no tenant data to lose. INV-23/INV-24/S-2 stay **vacuously** satisfied and are reported as vacuous, never as enforced. Revisit the moment a second tenant is real — *before* their first row lands, since retrofitting RLS onto populated tables is materially worse. **Superseded by ADR-P0-16.** |
| ADR-P0-12 | The ledger moved to its own `mlops` schema (migration 0043: `trial` + append-only `trial_event`, typed `outcome_vector`), in its own `ledger` crate — the only crate that can mint a `TrialTicket`. Supersedes the `backtest_trials` table of ADR-P0-01/06 | Keeping lifecycle columns on the trial row (ADR-P0-06's partial INV-19) | ADR-P0-06 had to leave INV-19 partial because state lived on the trial row. Moving every state change into chained, append-only `trial_event` rows makes INV-19 literal: no UPDATE and no DELETE anywhere in the ledger, and the chain covers outcomes too. Current state is a view (`trial_state`). A crate boundary makes the ticket's private constructor a compiler fact rather than a module convention. |
| ADR-P0-13 | The runtime pool connects as a restricted `platform_app` role (NOSUPERUSER, NOBYPASSRLS, member of `app_role`); migrations alone run as the owner. The password comes from `PLATFORM_DB_APP_PASSWORD`, set at boot | Connecting as the owner at runtime | The owner is a superuser, which bypasses every GRANT and every RLS policy — so none of the append-only grants or tenant policies would actually apply to the running platform. A migration must not carry a secret, hence the boot-time password. |
| ADR-P0-14 | When a symbol trades on several venues and a reader names none, the bar reader resolves to the single highest-quality venue (`venue_dim.quality_tier`, then lowest id) — never a blend | Blending venues, or erroring | SPEC §1.1 forbids blending; erroring would break every existing caller that names only a symbol. A deterministic, declared tier order gives one reproducible answer, and a caller that needs a specific venue names it. |
| ADR-P0-15 | Dedup semantics: a dispatch whose `config_hash` matches a prior terminal, non-deduplicated trial still registers, then settles `registered → deduplicated` naming that trial | Skipping registration on a cache hit | Trial accounting counts looks, not executions (§12.4). The jobs path registers inside the job-insert transaction so the job and its trial commit or roll back together. |
| ADR-P0-16 | FORCE RLS, transaction-local tenant context and tenant grants built **now** on every new `mlops` / `dataplane` table (migrations 0044, 0046, 0047). Reverses ADR-P0-11 | Deferring per ADR-P0-11 | ADR-P0-11's own trigger was "before a second tenant's first row lands". The new tables were empty, so building RLS cost nothing — whereas every row written before it would have had to be migrated under it. The tenant is the authenticated principal (`user_id`) and is never read from a request body. |
| ADR-P0-17 | The daily anchor is ed25519-signed (`PLATFORM_LEDGER_SIGNING_KEY`, required, no default) and written first to a write-once store (`FsWorm`: `create_new` + read-only file under `PLATFORM_WORM_DIR`), then to `mlops.ledger_anchor`. Anchors cover yesterday only; a broken chain is never anchored. Verification records every pass, pass or fail, in append-only `mlops.ledger_verification`. Tenants are discovered through a SECURITY DEFINER `ledger_tenants()` that returns ids only | S3 Object Lock; HMAC signatures; anchoring "today" | There is no object store with Object Lock in this stack; a filesystem store with `create_new` is honest about its guarantee and swappable behind `WormStore`. Asymmetric signatures let a verifier hold only public keys, and retired keys stay verifiable (`PLATFORM_LEDGER_RETIRED_KEYS`). Today's chain is still growing, so anchoring it would anchor a moving tip. The live test shows a forger who rewrites a row **and** rehashes the whole chain still fails against the signed head. |
| ADR-P0-18 | Agent trajectories are recorded inside `mcp_server_lib::dispatch_tool` (the untraced dispatcher is private with one caller, enforced by a static test) and POSTed to `/api/agent/trajectory`; harness-side tools that never reach dispatch (`finish_task`, inline waits, workspace `fs` tools) record themselves. `tool_schema_hash` = canonical-JSON sha256 of the full stamped descriptor | Logging in each driver separately | Three front doors (external MCP, internal driver, local driver) already share `dispatch_tool`; recording there means a new front door cannot forget. A step whose recording fails is counted (`Trajectory::unrecorded`) and logged, not silently dropped. Harness-internal loop tools (`search_tools`, `record_finding`) inside the sans-IO local loop are **not yet** recorded — reported as a gap in PROGRESS.md. |
| ADR-P0-19 | One feature runtime: every feature is a **windowed** implementation in `crates/features` evaluated through `dataplane::feature::EVALUATE_FN`, for training frames, backtests, warm starts and live serves alike. EMA and RSI are seeded at the oldest bar of a declared window (5·n and 5·n+1 bars); OBV is cumulative within a 256-bar window. A feature has no value until its whole window exists. The Python `features.py` duplicate is deleted | Keeping recursive EMA/RSI/OBV; SPEC's Polars runtime (ADR-009) | Recursive indicators depend on unbounded history, which no declared `lookback_bars` can describe and no windowed view can enforce (INV-13) — and they make a backfill that starts at a dataset edge disagree with a live serve that has full history (INV-14). Seed residual at 5·n bars is ≈ e⁻¹⁰. Partial-window values were rejected for the same parity reason. Polars: there is no Python/Polars runtime left in the serving path; one Rust implementation satisfies INV-14's actual requirement (one implementation, one evaluation function) without introducing a second language. Values change slightly from the recursive versions, so `EMA_FEATURE_VERSION` / `RSI_FEATURE_VERSION` were bumped to 2. |
| ADR-P0-20 | A live feature serve writes its `feature_serving_log` rows (with each feature's source `code_hash` and the max knowledge time of every row read) in the same request, before returning; a failed log write fails the serve. Features whose window is incomplete are returned as `null`, not `0.0` | Fire-and-forget logging; zero-filling absent features | "Written on every live serve" (§3.3) is only true if an unlogged serve cannot be returned. A fabricated zero is indistinguishable from a real zero downstream. |
| ADR-P0-21 | `N_eff` = number of clusters from **average-linkage** agglomeration (nearest-neighbour chain) on distance `1 − ρ` between UTC-daily compounded OOS return series, cut at ρ = 0.5; pairs with < 20 overlapping days count as independent. It is a sealed `ledger::neff::NEff` minted only by `TrialLedger::n_eff` over every stored series on the tenant's ledger, and Gate 3 takes that type | Eigenvalue-based effective rank; single/complete linkage; passing a count | SPEC §12.4 names correlation clustering over the whole ledger but no linkage or cut. Average linkage is reducible (so the O(n²) NN-chain is exact) and neither chains unrelated ideas together (single linkage) nor splits one noisy sweep (complete linkage). ρ = 0.5 means a majority of variance is shared. Thin-overlap pairs default to independent because the error must make deflation harsher, never more lenient. A sealed type makes "self-reported N_eff" unrepresentable, the same pattern as `TrialTicket`. Deduplicated and crashed trials contribute no series (a reused artifact is not a new test; a crash tested nothing) but every trial is in `trials_counted`. |
| ADR-P0-22 | Gate 3's primary p-value is **BHY**-adjusted within a family of `⌈N_eff⌉` tests, unobserved members entering at p = 1; the Šidák correction is deleted | Šidák / Bonferroni on the Experiment's look counter | §12.4: "BHY (FDR), not Bonferroni". Other candidates' p-values are generally not on record, and padding them with p = 1 is the one assumption that cannot flatter the observed test. Deleting Šidák removes the path rather than documenting it. |
| ADR-P0-23 | `SR_expected = min(SR − σ_SR·E[max of ⌈N_eff⌉ standard normals], 0.5·SR)` | "Just halve it"; DSR probability as a Sharpe | §12.4 defines the min but not "DSR-implied SR". Subtracting the expected maximum null Sharpe is the Sharpe-units quantity DSR tests against, so the haircut is non-linear exactly as the spec describes (weak Sharpes lose > 50%, strong ones are capped at half). |
| ADR-P0-24 | A backtest completion reporting a Sharpe must chain a persisted return series (`mlops.trial_return_series`, `returns_uri`) — enforced by CHECK `chk_event_returns_persisted` and mirrored in the in-memory ledger; a run with no usable equity curve settles with its portfolio metrics removed rather than unverifiable | Writing series to object storage; allowing completion without series | Series live beside the ledger under the same RLS and append-only rules, so N_eff can read them in one tenant-scoped query. A Sharpe without its return series can never be re-scored or clustered, so the schema refuses the combination. |
| ADR-P0-25 | The computed embargo is structural in fold generation: `features::walk_forward_folds` takes the pipeline's `EmbargoInputs` (horizon, longest declared feature lookback and knowledge lag from the single runtime, settlement) instead of a bare horizon, and uses `max(spec.embargo_bars, compute_embargo(inputs))`; purge stays `≥ horizon`. A spec can raise either and cannot lower them. Settlement lag is 0 on the training path | A validator callers may skip; allowing a lower embargo with a recorded override | §12.2 says the embargo is computed, never typed. Making the inputs a required argument means no caller can produce folds without stating the pipeline facts. The override path (lower + written reason) needs a reason field the walk-forward spec does not have, so lowering is simply not representable there until one exists — the stricter reading. Settlement is 0 because the training path only serves spot instruments that settle as they trade; a settling asset class must pass its lag before it can train. |
| ADR-P0-26 | Sealed holdout (§12.7): the **strategy lineage is the Experiment's `strategy_family`**. A request first inserts a `sealed_holdout_attempt` row, which *is* the claim — a partial unique index admits one first attempt per (tenant, lineage) before any holdout data is read. The evaluation's result is recorded once in `sealed_holdout_call` against the trial that produced it. A later request from any Experiment of the lineage is logged (`served_first_result = true`) and receives the first result with a notice (`VaultOutcome.notice`), running nothing. A claim whose evaluation never recorded a result leaves the lineage spent | Rate-limiting per Experiment (the old in-memory `holdout.spent`); claiming after the run; letting a crashed claim be retried | §12.7 says one evaluation per lineage, ever, enforced at the data tool. Per-Experiment limits let a new Experiment of the same idea re-peek. Claiming after the run lets two concurrent requests both read the holdout. A crashed evaluation may still have read holdout data, so retrying it would be a second look — the conservative reading is that the lineage is spent. |

## Phase 1 implementation ADRs (2026-09-14)

| ID | Decision | Rejected alternative | Reason |
|---|---|---|---|
| ADR-P1-01 | The training path declares `sample_weight_method = 'none'` on its label spec, which sets `overlapping_labels_unweighted = true` on every trial whose horizon exceeds one bar | Declaring `uniqueness` and computing average-uniqueness weights | §3.4 permits `none` and requires the consequence to be visible. The trainer sidecar applies no sample weights today, so declaring `uniqueness` would be a false claim on the trial that the comparison layer would then act on. `dataplane::label::uniqueness_weights` exists and is tested; wiring it through the sidecar's frame contract is the follow-up that lets the declaration change honestly. |
| ADR-P1-02 | `runtime_image_digest` = sha256 of `std::env::current_exe()`, computed once per process. REQUIRED, no default: a binary that cannot read its own image refuses to plan a dataset | A build-time constant (`GIT_SHA`, `CARGO_PKG_VERSION`); omitting the field when unavailable | §3.1 lists the digest as a hash input, and its purpose is to make "the same spec built by different code" a different dataset. A build-time constant does not change when the binary does (dirty trees, local builds), and a default would silently collapse every unknown build into one identity — the failure the field exists to prevent. This is not a container digest because nothing here runs in a container yet; when it does, the container digest is the better value and replaces it. |
| ADR-P1-03 | The `DatasetSpec` is resolved and hashed by `DatasetManager::plan` **before** the trial is registered, and `materialize` takes the plan. The split spec is built at the same point from the pipeline's `EmbargoInputs` | Hashing the dataset after materialization (the previous behaviour: hash of params ‖ Parquet bytes) | INV-12 requires the trial to name the data it will read. A hash over the produced bytes cannot be known until after the read, so the trial carried a placeholder (`data:<hash of the selection>`) — which is not a dataset id and does not imply byte-identical data. Resolving first also forces the surrogate instrument ids into the spec (§3.1: "materializing the resolved instrument list rather than re-running the universe query"). The split spec is a rule with a deterministic expansion (§3.5), so it is fully determined before the data is read; only the concrete fold index ranges depend on the realized row count. |
| ADR-P1-04 | The dataset's `feature_set_id` is the **versioned feature-DAG hash** (`features::runtime::feature_set_version_hash`, over each member's `(feature_id, version, code_hash)` in declared order), not the human-facing set name | Keeping `fs_core_ohlcv_v3` as the id | §3.1 calls the field a "versioned feature DAG hash". A name does not change when an implementation does, so a changed feature would have reused the old snapshot under the old id. The serving log keeps the human-facing ref plus per-feature `code_hashes`; the two are different jobs. |
| ADR-P1-05 | Snapshot objects are addressed by the spec hash (`dataset_id`), and re-materializing an existing `dataset_id` returns the pinned row without re-reading | Keying the object by a hash of its own bytes | The identity the ledger recorded and the identity the stored bytes carry must be the same string, or a trial's `dataset_id` cannot be resolved to an artifact. Byte-hash addressing also made the id unknowable before execution (see ADR-P1-03). |
| ADR-P1-06 | The random-label test's threshold is on the **t-statistic** of the mean out-of-sample return (limit 4.0), not on a Sharpe ratio, and the out-of-sample return is demeaned by the **training** block's mean | A fixed Sharpe limit (the spec's "Sharpe ≈ 0", AT-30's "\|Sharpe\| < 0.2") | Only the t-statistic has a calibrated null: the same Sharpe is noise on 200 observations and a finding on 200 000, so a fixed Sharpe limit silently changes strictness with sample size. Demeaning matters more than the threshold: without it the statistic is dominated by passive drift — an always-long position earns the sample's mean return at tiny variance and scores a "Sharpe" of 1.5 on pure noise, which is what the first implementation did. The train block's mean is used rather than the test block's, so the diagnostic contains no look-ahead of its own. Under a clean harness each permutation's t is ≈ N(0,1); a real leak lands in the tens, so nothing about this threshold is delicate. |
| ADR-P1-07 | The random-label probe is **two models — ridge and 1-nearest-neighbour — and the worse answer wins** | A single linear probe | A three-parameter ridge cannot memorize two thousand labels, so a harness whose test rows are inside its training rows looks perfectly clean to it — the exact defect the random-label test exists to catch. 1-NN catches memorization and nothing else. Neither alone is a leakage test. The fold-overlap case is *also* checked structurally (`fold_geometry`), because a question two index ranges can answer with certainty should not be left to one answered with a p-value. |
| ADR-P1-08 | Snapshot reproducibility replays the **stored spec verbatim** and refuses to run when the running binary's image digest differs from the one in the spec | Re-planning the dataset from its request each night | Re-planning stamps today's image digest and today's instrument resolution into the spec, producing a different `dataset_id` — a different dataset (ADR-P1-02), not a rebuild of this one. Refusing rather than comparing also avoids the alternative failure: after every deploy, every dataset would report a reproducibility violation, and an alarm that fires on every deploy is an alarm nobody reads. The dataset is counted `unrebuildable` and logged, never counted as a pass. |
| ADR-P1-09 | Master-clock densification applies **no maximum age**: a value is always carried forward, with its age and an `INTERPOLATED` flag, rather than dropped past a staleness bound | Emitting `None` past a `max_age_minutes` bound (which `dataplane::align::densify` supports) | §2 rule 1 is "emit staleness, never forward-fill *silently*" — the objection is to invisible staleness, not to staleness. A bound replaces a value the model could judge for itself ("this is 4300 minutes old") with a hole it cannot, and the spec explicitly says models may use age as a feature. Ticks before the *first* observation are still dropped, because there is no honest value for them. |
| ADR-P1-10 | A densified row's `ts_ns` is its **grid tick on the knowledge-time clock**, not the bar's own timestamp | Keeping the source bar's `ts_ns` | The master clock is the index (§2); the observation's time is an attribute of it, recoverable as `tick − age_minutes` (`MasterClockFrame::knowledge_ns`). Keeping the bar's timestamp would mean two instruments' rows at "the same" index were taken at different moments, which is the cross-asset alignment bug the master clock exists to prevent. |
| ADR-P1-11 | Per-feature staleness is the **age of the newest input** and the **union of quality flags across the declared window** | The decision row's flags alone | A feature that averages over a venue outage is as affected as one reading a single stale quote, and only the window-wide union says so. The age is the newest input's because that is what "how stale is this value" means; the window's oldest input is always `lookback − 1` bars old by construction and carries no information. |
| ADR-P1-12 | A null-world Run is a **different Run**: `RunConfig.null_world` carries the resolved `Null` plus the draw's seed and enters the content hash, and the generator is applied in `SimRunExecutor` at the one point a Run's data is assembled | Generating null data in the Study engine; varying only the seed on a `permutation_null` Study (the previous behaviour) | Varying the seed re-runs the real strategy on the real data, and calling that spread a null distribution makes every permutation p-value meaningless. Putting the null in the config means a null-world result can never share a `run_id` with the real result, the artifact cache cannot confuse them, and the ledger row says which world produced it. Applying it in the executor means no execution path can reach the simulator with a null-world config and real data. `StudyConfig` now requires the resolved `Null`, not just its id: a Study that carries only the id cannot build a null world, and `validate()` refuses it rather than silently degrading. |

| ADR-P1-14 | PBO is computed from a real `PBO_CONFIGS × PBO_PERIODS` (5 × 8) grid of Runs, not from a study's marginal distribution | Reusing the neighbourhood study's distribution | CSCV asks how often the configuration that looked best *in sample* underperforms *out of sample*. | ADR-P1-15 | The Experiment's counter gains `record_dispatches(n)` for Runs dispatched outside a Study (Gate 3's observed run and PBO grid) | Leaving direct Runs uncounted; wrapping them in synthetic Studies | §12.4 counts looks, not Studies. | ADR-P1-16 | The suite's synthetic executor keys its drift on `(strategy_ref, params)` rather than the whole `run_id`, and earns ≈ 0 in a null world | Keeping the `run_id`-keyed drift | With drift keyed on the whole `run_id`, a configuration's quality changed with the data window, so the in-sample best config was random and PBO sat at 0.5 for a strategy with a perfect edge — the fixture could not represent the thing the gate measures. Running both is the only comparison that can fail for the right reason. The squaring is not a fudge: the template reports variance per bar under a `variance_per_bar` key and the engine reports a per-bar deviation under a family named `..._vol`, both correctly labelled, and a second test asserts that shape separately so a change to either side fails saying which claim broke. | ADR-S4-04 | **A finding's `data_window` is the union of the windows of the results it cites**, and a finding whose window cannot be derived is recorded for the run and **not persisted** | Requiring the model to state the window; stamping the run's own window on every finding; refusing the finding outright | Resolves OQ-18 for the kind it actually blocked. **Derived, because the claim rests on the cited results and on nothing else** — the alternatives put a factual matter in the model's prose (where AGENT-011 keeps pulling things *out* of free-form strings, and where a model under pressure states the widest range it can) or stamp one window on a run that looked at two periods, which a comparison workflow does by definition. **The union rather than the intersection**: the intersection of disjoint windows is empty, so a claim resting on two periods would carry no window at all; and the union is the wider bound, so it reports more overlaps, so more pairs reach §2.2.1's conflict check — and P5 says conflicts are surfaced and never merged, so erring toward surfacing errs the way the spec wants. **Not a refusal, for now**: the analysis templates, `get_bars` and `preview_signals` all stamp a window and `run_backtest` does not, which is the most important evidence a finding can cite — refusing today would reject the central case. So the finding is held for the run exactly as before and says out loud that it did not persist.
