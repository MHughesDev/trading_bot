# The coverage census, 2026-09-15

**The number nobody had.** The roadmap's stage ordering rested on a single
observation from 2026-09-08 — "BTC-USD holds 22 one-hour bars". That observation
was true and it was badly misleading. Here is what is actually on disk.

Measured directly against the live ClickHouse `market_bars_v2` on 2026-09-15, using
the same arithmetic the census code implements (`dataplane::census`).

---

## 1. Headline

| Question | Answer |
|---|---|
| Total bar rows | **158,259** |
| Distinct instruments | **4** (+1 synthetic) |
| Timeframes | **2** (1m, 1h) |
| Deepest **continuous** 1m coverage | **30.8 days** (ETH-USD @ coinbase, 44,385 bars) |
| Deepest **continuous** 1h coverage | **88.1 days** (BTC-USDT @ coinbase, 2,115 bars) |
| Rows whose knowledge time was **observed** | **0** |
| Rows whose knowledge time is **unreliable** | **158,259 — all of them** |
| `strict_v1` Gate 9 (5 y / 1,826 d) satisfied by | **nothing** |
| `paper_v1` (1 y / 365 d) satisfied by | **nothing** |

**The "22 bars" figure was one venue, one timeframe, one instrument.** BTC-USD
actually holds 92,013 1m bars from Coinbase over a 119-day span. The platform has
roughly a hundred times more data than the anecdote implied — and still nowhere
near enough for either gate profile.

The BTC-USD / coinbase / 1m series is the platform's best real asset and it is
**two blocks, not one**: 44,230 continuous bars, then a 76,360-period hole (53

31 days of history plus a second, later fragment.

Read the last column, not the third. Total bar count over a swiss-cheese span is
the number that makes thin data look adequate.

## 4. The finding that matters most

**Every row in `market_bars_v2` carries `available_time = event_time`. All 158,259
of them.**

| Instrument | TF | Source | `available == event` | `available > event` |
|---|---|---|---|---|
| BTC-USD | 1h | coinbase_rest | 22 | 0 |
| BTC-USD | 1m | coinbase_rest | 93,453 | 0 |
| BTC-USD | 1m | kraken_rest | 3,049 | 0 |
| BTC-USD | 1m | kraken_ws | 10,002 | 0 |
| BTC-USDT | 1h | coinbase_rest | 2,281 | 0 |
| ETH-USD | 1h | coinbase_rest | 48 | 0 |
| ETH-USD | 1m | coinbase_rest | 44,387 | 0 |
| ETH-USD | 1m | kraken_ws | 17 | 0 |
| SYN-PLANTED-AR1 | 1h | synthetic | 5,000 | 0 |

Min and max lag are both **0 seconds**, for every source including the three REST
backfill sources. This is the bug `clickhouse/07_canonical_market.sql` documents —
v2 stamped REST backfills as knowable at the bar close — and it is total, not
partial. **The platform currently cannot distinguish a bar it watched arrive from
one a REST endpoint handed it weeks later.**

Consequences:

- Gate 15 takes forward evidence from observed-knowledge rows only (D-P3). On this
  data there are none it can trust, so **no existing bar is admissible as forward
  evidence**, whatever its timestamps say.
- Any backtest over this history has been reading bars as knowable at their close.
  For a 1m bar the overstatement is bounded by the vendor lag (~60 s), which the
  computed embargo usually dominates — which is why ADR-P2-24 says *flag, never
  block*. It is a real distortion, not a catastrophic one, but it is **unmeasurable
  from the data itself** because nothing records which rows are affected.

### And the canonical store is not there

`market_bar` — the table `BarStore` reads and writes, and the one that would carry
`BACKFILLED_KNOWLEDGE_TIME` — **does not exist in the live ClickHouse database.**
`SHOW TABLES` on 2026-09-15 returned: `backtest_run_equity`, `backtest_run_trades`,
`market_bars`, `market_bars_rescue_20260911`, `market_bars_v2`,
`market_bars_v2_premerge_20260911184559`, `market_trades`, `model_predictions`,
`model_traces`. No `market_bar`, no `restatement_index`, no dimension tables.

The DDL is replayed on platform boot by `storage::clickhouse::migrate`, so this
install has not booted the platform since 07 landed, and the v2 → canonical copy
has never run here. Until it does, **every `BarStore` read on this machine returns
nothing** — which is why the census code could not be run end-to-end and these
numbers were taken by direct query instead.

That copy is the step that would flag all 158,259 rows honestly. It should be run
before anything trusts a `BarStore` read on this box.

---

## 5. What this changes

1. **The evidence clock is worse than the roadmap assumed, in the dimension that
   matters.** Not bar count — provenance. There is more data than believed and
   *none* of it is usable as forward evidence.
2. **`strict_v1` is not reachable this decade from live collection alone.** Deep
   backfill (Phase 1) is the only path, and Kraken's 1-year funding window is a
   reminder that free history windows roll — every month of delay is a month that
   falls off the far end.
3. **`paper_v1` carries the programme**, as ADR-P2-14 anticipated, and even it is
   ~11 months away for the best series without backfill.
4. **The forward collectors are the only source of trustworthy knowledge times the
   platform will have.** Their first row is the first row Gate 15 can ever use.

---

## 6. How to reproduce

The census code is `dataplane::census` (pure) and `backtest::census` (runner,
writing `dataplane.data_coverage_census`, migration 0097). Once `market_bar` exists
and the canonical copy has run, `backtest::census::take_census` reproduces this
table through the PIT reader, with `derived_knowledge_bars` populated from the
`BACKFILLED_KNOWLEDGE_TIME` flag rather than left unknowable.

The figures above were taken with direct SQL against `market_bars_v2` because the
canonical store does not yet exist on this install. They are the same arithmetic;
the one column they cannot fill honestly is the observed/derived split, which is
§4's point.
