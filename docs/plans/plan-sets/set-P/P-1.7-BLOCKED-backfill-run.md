# P-1.7 — the run did not happen, and why

**Depth achieved by this task: zero bars, on every instrument and every
timeframe. Days removed from the `paper_v1` and `strict_v1` dates: zero.**

That is the honest headline and it belongs first. The machinery P-1.1…P-1.6
built is tested and ready; it has never been pointed at a venue, because the
platform's databases are not running on this box.

---

## 1. The blocking chain, measured

Three links, in the order they have to be fixed.

| # | Fact | How it was established |
|---|---|---|
| 1 | **The Docker daemon is not running.** | `docker ps` → `failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine … The system cannot find the file specified` |
| 2 | **ClickHouse and Postgres are therefore unreachable.** | `curl http://localhost:8123/ping` → exit 7 (connection refused), 2026-09-15 |
| 3 | **`market_bar` — the canonical table `BarStore` reads and writes — does not exist in the live database**, so even with the containers up, every `BarStore` read returns nothing until the platform boots once. | Track 3's census, [P-0.1](P-0.1-CENSUS-2026-09-15.md) §4: `SHOW TABLES` returned nine tables, none of them `market_bar`. |

### Link 3 is **not** a missing migration — do not write one

`clickhouse/07_canonical_market.sql`, which creates `market_bar`, is already
embedded and replayed on every platform boot:
`crates/storage/src/clickhouse/migrate.rs`, `MIGRATIONS`, entry
`07_canonical_market.sql`. Every statement is `CREATE TABLE IF NOT EXISTS`, so
replay is a no-op once the table exists.

The table is absent for one operational reason: **this install has not booted
the platform binary since Set L Phase 0 landed.** Adding a migration would be
fixing a symptom that is already fixed in code.

The same reason explains `migrations/0099_backfill_state.sql`
(`dataplane.backfill_state`, this phase's cursor): it exists, it is embedded by
`sqlx::migrate!`, and it has never been applied here because nothing has
connected to Postgres to apply it.

### The unblock, in order

1. Start Docker. Project memory records that this box crash-loops on
   un-deletable phantom sockets and that `Docker\run` must be renamed aside
   before every launch — that is a human step and this task did not attempt it.
2. Boot the platform once. `storage::clickhouse::migrate::run_migrations`
   creates `market_bar`, `restatement_index` and the dimension tables;
   `storage::postgres::run_migrations` applies 0099.
3. Run the `market_bars_v2` → `market_bar` canonical copy
   (`storage::clickhouse::canonical`), which is what flags the existing 158,259
   rows honestly. **Track 20 owns that repair**; this task owns only that new
   writes are honest from the first row (P-1.6, done).
4. Then run this task: submit the windows in §3 and re-run the census.

Roadmap gate: **§8, human/credential class.** Nothing here needs a decision
about data policy — it needs the machine's containers started.

## 3. What the run should do when it is unblocked — aimed, not uniform

The census says the platform's *only* deep real series is Coinbase, and that
BTC-USD 1m is **two blocks with a 53-day hole between them**, not 119 days of
history. So the run is three jobs, in this order:

| Order | Window | Source | Why first |
|---|---|---|---|
| 1 | BTC-USD 1m, the 76 360-period hole inside the existing span (2026-06-08 → 2026-07-31 approx.) | `coinbase_rest` | Closing an interior hole converts 30.7 d of continuous coverage into ~119 d in one pass — the cheapest days on the board by a wide margin. |
| 2 | BTC-USD and ETH-USD 1m, 2023-09-15 → the start of existing coverage | `coinbase_rest` | The D8 target. |
| 3 | The same two, 1h and 1d, same span | `coinbase_rest` | Coarse timeframes are nearly free and 1h is currently 22 bars for BTC-USD. |

**Do not aim job 1 at Kraken.** BTC-USD 1m at Kraken is 90.13 % missing over its
own span, and Kraken's public `OHLC` endpoint does not paginate 1m history
backwards — it serves the most recent 720 minutes only. Kraken depth comes from
the downloadable archives (P-1.3's second path), which are a human download.

### The cost, derived from the venues' published page caps and our declared limits

Not measured — **derived**, and to be replaced with measurements when the run
happens.

| Source | Page cap | Declared limit | Requests for 3 y of 1m | Wall clock |
|---|---|---|---|---|
| Coinbase Exchange candles | 300 candles | 8 req/s | ≈ 5 260 per instrument | **≈ 11 min** per instrument |
| Alpaca crypto bars | 10 000 bars | 190 req/min | ≈ 158 per instrument | **≈ 50 s** per instrument |
| Kraken public OHLC | 720 candles | 1 req/s | not applicable — no 1m backpagination | — |

If those numbers hold, **the entire D8 target for both instruments is roughly
half an hour of polite requests.** The gap that puts `strict_v1` in 2031 is not
expensive to close; it has simply never been attempted. That is the finding this
task exists to produce, and it survives the run not having happened.

## 4. The escalation, stated as a decision

The plan anticipated one possible finding — "three years is not available from
any free source" — and asked for it to be quantified and escalated rather than
quietly absorbed. **That is not the finding.** Nothing observed here suggests
the free sources cannot serve three years of 1m crypto history; Coinbase's
public candle endpoint has no documented history floor for BTC-USD, and the
arithmetic above says the fetch is cheap.

So there is **no ADR-0027 revisit to cost yet**, and this task must not create
one. What goes to the roadmap's §8 gates instead is smaller and more awkward:

> **The only thing between the platform and a three-year 1m history is that
> nobody has started the containers on this machine and booted the platform
> once.** The blocker for `strict_v1`'s five-year floor is operational, not a
> data-policy question.

Two things follow that the user should decide:

1. **Who runs the box?** Every remaining Set P acceptance — the census through
   the PIT reader, the grades in Phase 2, this run — needs a live ClickHouse and
   Postgres. A programme whose evidence clock is measured in years cannot have
   its data plane gated on an ad-hoc `docker start`.
2. **Confirm the free-history depth before planning around it.** The §3 table is
   arithmetic over documented page caps, not a measurement. The first hour of
   the actual run replaces every number in it, and the plan's own risk register
   lists "the census reveals depth is far worse than believed" as the outcome to
   take seriously rather than argue with.

## 5. What *is* ready

Everything except the run.

- The `backfill` job kind, the durable cursor, migration 0099, and the
  resume/idempotency/rate-limit properties — proved by counting adapter calls
  (`crates/jobs/tests/backfill_resume.rs`).
- Coinbase, Kraken (both paths) and Alpaca adapters, with declared limits
  honoured by a limiter that **refuses** rather than sleeps
  (`crates/collectors/src/backfill/`).
- Backfilled rows permanently distinguishable from observed ones, with the
  provenance decision keyed on the **receipt, per row**, and the sources'
  maximum declared lag reaching `EmbargoInputs` (`crates/dataplane/src/knowledge.rs`,
  `features::walk_forward::embargo_inputs_over`).
- The end-to-end ClickHouse assertions are **written and compiling but unrun**
  (`crates/backtest/tests/backfill_revisions.rs`); they print `SKIPPED … this
  proves nothing` without `BACKTEST_E2E_CLICKHOUSE_URL`, so a green run without
  a database cannot be mistaken for evidence. They are the first thing to run
  after step 2 of the unblock.
